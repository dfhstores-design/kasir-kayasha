# PHASE-03 — Katalog, Foto Produk, dan Penjualan Langsung

- **Fase:** Phase 3 — katalog, foto produk, dan penjualan langsung (lokal/offline)
- **Tanggal/waktu lokal:** Selasa, 10 November 2026, 15:10 WIB (Asia/Jakarta)
- **Repo:** <https://github.com/dfhstores-design/kasir-kayasha>
- **Agent:** DeepSeek Harness
- **Hasil singkat:** barang bisa ditambah + foto terkompresi, dijual, dan tersimpan menjadi transaksi
  **sungguhan** di IndexedDB. Lulus lint + typecheck + **135 tes** + build, dan alur penuh
  **diuji di browser** (online & offline).

---

## 1. Tujuan

Membuat alur inti pameran benar-benar berfungsi:

1. **Admin barang** — tambah/ubah/arsipkan barang, stok gudang, maks 3 foto.
2. **Foto** — ambil dari kamera/galeri, dikompres di perangkat, **dengan indikator progres wajib**.
3. **Penjualan langsung** — pilih lewat grid/cari → detail → keranjang → simpan transaksi.
4. **Diskon & ongkir** di keranjang, plus jenis bayar dan status bayar.
5. **Transaksi tersimpan** — nomor resi berurutan, stok berkurang, snapshot tersimpan.

## 2. Permintaan tambahan dari pemilik

> **"wajib ada indikator progress ketika upload foto"**

Diterapkan sebagai aturan tetap (bukan tambahan opsional):

| Tahap | Tulisan | Persen |
| --- | --- | --- |
| baca berkas | `Membaca foto…` | 0 |
| kecilkan ukuran | `Mengecilkan foto…` | 15 |
| kompres | `Mengompres foto…` | 40 |
| simpan | `Menyimpan foto…` | 85 |
| selesai | `Foto siap` | 100 |

Ada dua indikator terpisah: **proses** (di perangkat) dan **unggah** (Phase 6). Pada Phase 3 baris
unggah berbunyi **`Tersimpan di perangkat`** — jujur menyebut belum dikirim ke cloud.

## 6a. Tambahan sesi yang sama — foto resolusi tinggi >80 MB

Permintaan pemilik setelah Phase 3 dianggap selesai: *"perlu antisipasi ukuran foto yang diupload
memiliki resolusi tinggi dengan ukuran 1 file >80MB"*.

### Masalah nyata sebelumnya

`kompresFoto` memanggil `createImageBitmap(file)` tanpa batas lalu `drawImage` ukuran penuh.
Foto 108 MP ≈ 12000×9000 membutuhkan **±432 MB RAM** (RGBA). Di HP Android tab akan **crash** —
bukan error yang bisa ditangkap `try/catch`. Jadi pemeriksaan harus terjadi **sebelum** decode.

### Yang ditambahkan

| Lapis | Isi |
| --- | --- |
| `periksaBerkasFoto` | tolak bukan-gambar, tolak >150 MB, tandai >10 MB sebagai "besar" |
| `periksaResolusi` | tolak di atas 150 MP |
| `perlukecilkanSaatDecode` | hitung perkiraan memori (4 byte/piksel) vs batas 320 MB |
| `jalurPengecilan` | pengecilan bertahap, maks 2× per langkah || decode hemat | `createImageBitmap(file, { resizeWidth: 1600 })` untuk berkas besar |
| pengecilan bertahap | kanvas perantara bila sumber masih >2× target |
| `KompresiError` | kode galat + pesan Bahasa Indonesia yang bisa ditampilkan |

### Hasil uji di browser (bukan asumsi)

| Uji | Hasil |
| --- | --- |
| Foto **48 MP, 43,9 MB** | ✅ **1600×1200 WebP, 329 KB** (dalam target 250–400 KB) |
| Foto **160 MB** | ✅ ditolak **sebelum** decode; pesan `Foto terlalu besar (160.0 MB). Maksimal 150 MB.`; jumlah foto tetap 1; **tanpa** batang progres |
| Foto 3000×2000 (104 KB) | ✅ 1600×1067 WebP 6 KB |

Tambahan tes: **+21** (12 → 33 di `kompresiFoto.test.ts`), termasuk bukti bahwa
`createImageBitmap` **tidak dipanggil** untuk berkas 200 MB.

### Perbaikan kecil dari uji visual

Pesan "terlalu besar" sempat tampil **dua kali** (panel progres + baris hint). Kini pesan galat
hanya di panel progres; hint tidak diulang.
